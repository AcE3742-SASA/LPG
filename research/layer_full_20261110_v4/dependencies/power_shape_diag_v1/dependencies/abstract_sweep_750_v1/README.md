# 동일 200형상 GEMM 재측정 — 750 MHz

코어 750 MHz, 메모리 6801 MHz, 기존 전력 한도 70 W에서 기존과 동일한 200형상을 새로 측정한다. 200형상 × FP16/FP32 × allocate/prealloc/Graph × 세 라운드 = **3,600측정·25,200블록·1,200묶음**이다. 기존 780 MHz 부분수집과 합치지 않는다.

## 실행

ZIP의 `abstract_sweep_750_v1` 폴더를 Ubuntu `/home/eu/gemm-research/scripts/` 아래에 둔다. 기존 의존 폴더와 `ai_env`를 유지한다. 최근 재진단 원본 폴더 `clock_recheck_v1/runs/clock_recheck_20260921_143452_YZ9HN5`도 그대로 필요하다. 환경 재설치는 없다.

```bash
bash /home/eu/gemm-research/scripts/abstract_sweep_750_v1/launch.sh
```

현재 tmux 세션·창을 그대로 쓴다. 새 세션이나 창을 생성하지 않으며 종료 후 Enter 입력을 기다리지 않는다. tmux 안에서 분리는 Control+B를 누르고 손을 뗀 뒤 D다. tmux 밖이면 현재 터미널에서 실행하므로 완료까지 SSH 연결을 유지한다.

시작 시 소스검사 `PASS`, `tasks: 3600`, `triplets: 1200`을 확인한다. 이어 재진단의 **750 MHz 단계만** 기존 분석기로 읽기 전용 재검산한다. 검토한 manifest·결과·센서 hash, 소스사본, 정확성·시간·클럭·해제 근거가 일치해야 새 부하를 시작한다. 전체 재진단의 REVIEW와 마지막 780 MHz 문제는 그대로 보존한다. 750 MHz의 세 형상 통과를 200형상 전체 통과로 간주하지 않는다.

`Worker log:` 다음에는 표시된 파일에 진행 상황이 기록된다. 첫 180초는 예열이고 이후 `[1/3600]`처럼 진행된다. 필요하면 다른 SSH 터미널에서 아래처럼 마지막 부분만 확인한다.

```bash
tail -n 20 'Worker log에 표시된 worker_0.log의 전체 경로'
```

계획 예산은 **약 5~6시간**이다. 기존 작업당 약 3.9초로 3,600건은 약 3.9시간이며 형상별 준비·검산 차이를 포함한 추정이다. 시작·재시작 때 여유 디스크 20 GiB와 다른 GPU 작업 여부를 확인한다. 다른 GPU 작업을 강제 종료하지 않는다. 측정 중에는 다른 GPU 실험과 절전·재부팅을 피한다.

## 유지한 구성

- `selection.json`과 `subset.py`는 기존 780 MHz 실행본과 바이트 단위로 같다. 기존 5,002후보에서 형상 크기·종횡비·8배수 정렬·2의 거듭제곱 근방의 32층으로 고른 200개다. 10개 기하학적 기준점을 포함하고 fresh holdout 1,000형상은 제외한다. 결과를 보고 형상을 다시 고르지 않았다.
- 기존 task ID·입력 seed·split·세 라운드의 형상 및 방식 순서는 같다. 추가 대조·경계·연산 기준 phase나 예측기 학습을 실행하지 않는다. 원래 113,382측정 및 옛 10,000조건 세 방식 전수 재측정 계획은 유지한다.
- 기존 v6 Timer, CUDA Event, 180초 예열, 측정마다 3,000 event ms 안정화, 약 100 ms 목표 7블록, 정확성 검사와 5% 변동 기준을 유지한다. 전체 출력 정확성 비교 36측정·표본 비교 3,564측정이다.
- 기존 48개 형상/정밀도 Graph 묶음에 재진단에서 사용한 문제 형상의 두 값을 추가 고정했다. `(3128,680,488)` FP32는 Graph당 GEMM 5개, FP16은 20개다. 겹치는 대조 조건은 기존 값과 일치해야 한다. 나머지는 기존 방식으로 최초 선택 후 이어쓰기에서 유지한다.
- 전력 한도는 바꾸지 않고 70 W인지 확인한다. 코어/메모리 클럭 설정과 해제는 sudo로, 실제 측정은 기존 `ai_env`의 일반 사용자로 실행한다.

## 종료와 이어하기

결과는 `abstract_sweep_750_v1/runs/abstract_200_750`에 저장된다. 종료하면 같은 `runs` 아래에 `abstract_200_750_날짜_식별자.zip`과 SHA-256 파일이 생성되고 `RESULT_ZIP=...`가 표시된다. **그 ZIP을 반환하면 검토한다.**

정확성·실행 FAIL은 해당 기록을 저장한 뒤 중단한다. 시간 변동만의 REVIEW는 수집을 이어간다. 120작업 묶음마다 센서를 분석하며 클럭 이탈·순간 전력 제한·센서 문제가 확인되면 다음 묶음 전에 중단한다. 누적 전력 카운터 해석 문제만으로 중단하지는 않으며 별도 기록으로 남긴다.

Ctrl+C나 처리 가능한 종료 신호를 받으면 worker 종료를 기다리고 코어·메모리 고정을 해제한다. 로그·이전 시도·블록·센서·소스·해제 근거를 보존해 실패나 중단도 가능한 자료를 ZIP으로 만든다. GPU 잠금과 출력 폴더 잠금은 기존 방식을 유지한다.

정상적으로 저장되고 센서 품질도 통과한 부분 실행은 **같은 명령**으로 이어갈 수 있다. 재시작 전 저장된 원자료와 센서를 재검산하므로 DB의 원래 PASS 표시만 믿고 문제 기록을 건너뛰지 않는다. 클럭·센서·데이터 문제가 남아 있으면 설정 변경 전에 `resume refused`로 중단한다. 이 경우 결과 ZIP을 먼저 검토하며, 새 출력 경로는 원인 확인 후 사용한다. 기존 raw FAIL의 `--retry-failed`도 원인 검토 후에만 사용한다. 프로토콜이나 소스가 다른 결과에는 이어쓰지 않는다.

누적 SW Power Cap 카운터 해석 미해결 때문에 모든 측정이 통과해도 전체 `REVIEW`·exit 2가 남을 수 있다. 완료 확인은 다음을 함께 본다.

- `recorded=3600`, `missing=0`, `FAIL=0`
- `timed_blocks=25200`, `triplets_complete=1200`
- `round_groups_complete=1200`, `timing_and_sampled_clocks_pass=true`
- 코어·메모리 해제 명령 성공과 최종 ZIP 생성

첫 라운드뿐이면 라운드 간 변동은 `null`로 표시하고, 조건별 확보 라운드 수와 세 라운드 완료 그룹 수를 별도로 남긴다. 일부 조건의 두 라운드 변동이 계산되더라도 전체 세 라운드 검증과 구분한다.

## 해석과 로컬 확인

표본 클럭은 연속 클럭 유지나 유효 커널 주파수를 보증하지 않는다. 약 100 ms 블록의 호출당 평균과 단일 호출 분포를 구분한다. 세 라운드는 재시작 전까지 같은 worker 내 반복이다. 세 방식의 차이를 정확한 할당 비용·CPU 대기 시간으로 해석하지 않는다. 누적 카운터 미해결과 이전 실행 간 약 2% 차이도 보존한다.

```bash
python3 -B abstract_sweep_750_v1/run.py verify
python3 -B abstract_sweep_750_v1/test_subset.py
```

측정과 클럭 해제 경로는 기존 구현을 재사용한다. 변경은 750 MHz 설정·판정, 검토한 750 단계 연결, Graph 두 조건 추가 고정, 센서 품질을 반영한 재시작 차단, 부분 라운드 표시와 패키지 경로다. 기존 의존 63파일의 hash를 고정한다. Mac 로컬 검사는 실제 200형상 GPU 측정 성공을 뜻하지 않는다.
