## 2. FAIL 원인: 프로파일러 완료 판정 오류

Nsight Compute 2026.3.0.0의 실제 종료 코드는 **0**이다. 218,167바이트의 `capture.ncu-repz`와 실제 GEMM 커널·측정값을 담은 696열 CSV가 생성됐다. 기존 코드에는 두 가지 잘못된 가정이 있었다.

1. 보고서가 반드시 `capture.ncu-rep`라는 이름일 것으로 가정했다. 이번 실제 출력은 `capture.ncu-repz`였다.
2. `--page raw --csv` 출력에도 `Metric Name` 열이 있을 것으로 가정했다. 실제 CSV는 커널이 행, 개별 metric이 열인 형식이었다.

이 FAIL의 원인은 CUDA 계산 오류나 프로파일러 권한 오류가 아니다. 로그의 unmodified GPU clocks 경고는 `--clock-control none`으로 실행했기 때문에 남은 것으로, 프로파일러 종료 실패를 뜻하지 않는다. NVIDIA 문서도 CSV 출력과 출력 page를 구분한다. [Nsight Compute CLI 공식 문서](https://docs.nvidia.com/nsight-compute/NsightComputeCli/index.html#console-output)

관측한 커널 이름은 `cutlass_80_wmma_tensorop_f16_s161616gemm_f16_32x32_128x2_nn_align8`을 포함한다. 이 한 작업의 이름과 카운터를 모든 GEMM의 실행 경로나 Tensor Core 사용 비율로 일반화하지 않는다. `--cache-control all`로 얻은 프로파일링 수치는 일반 타이밍 데이터에 합치지 않는다.

v4는 `.ncu-rep`와 `.ncu-repz`를 모두 인정하고, Python 표준 CSV 파서로 실제 커널 ID·이름과 유한한 metric 값이 있는지 검사한다. 종료 코드가 0이 아니거나 보고서가 비어 있거나 CSV에 헤더만 있으면 계속 FAIL로 처리한다. 업로드된 실제 로그를 새 검사에 통과시켰고 관련 회귀 검사도 통과했다. 기존 결과는 분석상 오판으로 설명하되 원본 FAIL 기록은 그대로 둔다.

### round 사이에서 달라진 15조건 묶음

주 측정 13묶음, 연산 기준 1묶음, pressure 대조 1묶음이다. 여기서 차이는 `(최대 round 중앙값 − 최소 round 중앙값) / 두 중앙값의 중앙값`이며, 15개 GPU 실행이나 15개 독립 형상을 뜻하지 않는다. 최대 차이는 27.8%였다. [전체 비교표](between_round.csv)

대표적으로 (3216, 520, 776) FP32는 381→491 μs였고 각 round의 IQR은 0.274%, 0.584%였다. 해당 타이밍 구간 내부의 1초 간격 telemetry에는 각각 56°C·1185 MHz, 72°C·900 MHz가 기록됐다. (1016, 2048, 504) FP32도 260→343 μs였다. 이 조건의 round 1 타이밍 구간 내부에는 telemetry 표본이 없어 정밀한 동시 대응은 주장하지 않는다.

GPU 온도는 전체 세션에서 36~75°C였다. 측정 중 온도 상승·클럭 하락과 실행시간 증가가 함께 관측돼 초기 열 상태 차이가 유력한 점검 대상이다. 다만 전력 제한, 이전 작업, 실행 순서, 다른 GPU 클라이언트 등과 분리한 인과 실험은 아니며 열 스로틀링을 확정할 수 없다. 1초 간격 telemetry는 짧은 작업의 모든 변화를 포착하지 못한다. 타이밍 구간 내부 표본만 연결한 표는 [main_telemetry_alignment.csv](main_telemetry_alignment.csv)에 있다.

v4는 시작 예열을 10초에서 180초로 늘렸다. 이는 개선을 시험하기 위한 변경이며 안정화 완료를 자동 보장하지 않는다. 개별 조건의 관측된 settle 750 ms, 7블록, IQR·drift·round 차이 5% 기준은 유지한다. 기존 데이터의 큰 차이를 허용하도록 임계값을 완화하지 않는다.

## 4. 확장초록에 활용할 수 있는 예비 관측

FP16의 N 경계 현상은 이번 prealloc 측정에서도 두 round에 걸쳐 관측됐다.

| 형상 변화 | round 0 | round 1 |
|---|---|---|
| (1024, 64, 264) → (1024, 65, 264) | 4.87→9.71 μs | 4.92→9.84 μs |
| (136, 256, 4096) → (136, 257, 4096) | 14.2→26.7 μs | 14.4→27.2 μs |

각 쌍은 이번 블록·round 기준을 통과했다. 기존 10,000조건의 출력 할당 방식과 새 prealloc 방식은 다르므로 원자료를 하나의 동일 프로토콜 데이터셋으로 무조건 합치지 않는다. 경계 차이의 커널 수준 원인은 나머지 프로파일링을 완료하고 비교해야 한다.

작은 연결 실험은 batch 64, 폭 256→512→128인 GEMM 두 층이다. 12작업 모두 저장된 층별 정확성 검사와 변동 기준을 통과했다. 아래 값은 각 블록에서 계산한 `(연결 시간 − 개별 시간 합) / 연결 시간`의 중앙값이며, 개별 중앙값끼리 다시 계산한 비율과 구분한다.

| dtype | 실행 방식 | round 0 잔차 | round 1 잔차 |
|---|---|---:|---:|
| FP32 | 연속 제출 | −0.627% | −0.862% |
| FP32 | 층 사이 동기화 | +27.5% | +27.4% |
| FP32 | Graph | +0.810% | +0.707% |
| FP16 | 연속 제출 | +2.33% | +2.44% |
| FP16 | 층 사이 동기화 | +41.1% | +41.0% |
| FP16 | Graph | −0.694% | −0.817% |

[연결 실험 원래 정밀도의 결과표](chain_results.csv). 동기화를 개입했을 때 조립 잔차가 달라지는 예비 관측으로 쓸 수 있다. 작은 두 층 사례이므로 전체 신경망에 일반화하지 않는다. 서로 다른 방식은 Graph batching 등 조건도 달라 차이 전체를 순수 launch 비용이라고 해석하지 않는다. 예측기는 아직 학습하지 않았으므로 이 표는 예측 정확도 결과가 아니다.
