# 780 MHz 연산 천장: 커널 후보 비교

실제 GPU에서 통과한 v3 실행 코드를 재사용해, 기존 설치에서 확인한 FP32 SIMT 8개와 FP16 입력·출력/FP32 누산 Tensor Core 8개를 8192³에서 한 번씩 비교한다. 16개 커널과 자료 배치의 정본은 기존 inventory 원행을 읽어 만든 `kernels.json`이다. 각 정밀도마다 2개 커널 구성 × A/B의 nn·nt·tn·tt 배치 4개이며 C/D는 column을 유지한다. TF32·sparse·다른 자료형·새 빌드는 추가하지 않는다.

원래 run_one에 A/B 배치 인자를 추가하고 출력 행이 해당 배치와 정확히 일치하는지 확인한다. 공유 GPU 잠금, 다른 계산 프로세스 검사, 780/6801 MHz 재설정, 70 W 확인, device 검증, 동일 입력·예열·profiling 조건, 커널별 부하 클록 검사, 실패 시 후속 중단, 원로그와 압축 보존은 v3에서 유지한다. 무부하 클록을 목표와 같아야 한다고 요구하지 않는다. 종료 시 고정은 해제하지 않는다.

`cutlass_780_kernel_compare.sh` 한 파일만 Ubuntu `/home/eu/`로 옮긴 뒤 `bash /home/eu/cutlass_780_kernel_compare.sh`를 실행한다. 16개 PASS·종료코드 0이 통과 기준이며 실패해도 마지막 tar.gz를 전달한다. 소요시간 약 3–5분은 이번 두 커널의 전체 실행 약 23초를 16개로 외삽한 예상이며 아직 측정한 값이 아니다.

이는 단일 형상에서 후보를 고르는 단계다. 한 번의 최고값을 최종 천장으로 확정하지 않고, 후보를 고른 뒤 크기별·독립 반복으로 중앙값과 변동을 확인한다. 최종 원자료가 오면 출력 순서에 따른 변화와 기존 smoke 커널의 재현성도 함께 검토한다.

로컬 `python3 -B test_compare.py`는 16개 실제 inventory 이름·A/B/C/D 배치가 정확히 한 번씩 호출되는지, 첫 검증 실패 및 배치 불일치에서 후속 호출이 중단되는지, 로그 압축과 모니터 종료를 확인했다. 기존 v3에서 이미 검증한 나머지 보호 조건은 유지했다. 새 GPU 실행은 하지 않았다.
