# 750·780·810 MHz 결과 검토

240측정·1680블록·80개 세 방식 묶음을 모두 수집했다. 측정별 시간·관측 클럭 기준은 전부 PASS다. 전체 REVIEW는 누적 전력 제한 카운터와 순간 표본의 불일치 때문이다. 최종 클럭은 아직 선정하지 않았고 full은 HOLD다.

## 원본과 검산

- 원본: `clock_lower_20260920_192959_la2ofx.zip`
- SHA-256: `14f811def2c5b1592fd87a048b928c1b4cc7fd9cc349daa9f2c6826d81e692aa`
- 381파일 CRC·개별 hash 확인, 원본 바이트 보존. 자체 7개·의존 42개 소스가 배포본 및 manifest와 일치한다.
- 검증한 로컬 분석기로 일곱 산출물을 재생성해 원본과 바이트가 같고 summary 객체도 일치함을 확인했다. ZIP 안의 코드를 실행하지 않았다.
- 작업 순서·입력·Graph 묶음·분모·시간 통계·저장된 정확성 검사 기록을 확인했다. 전체 출력 검사 48회, 256원소 표본 검사 192회가 통과했다. GPU에서 정확성 검사를 다시 실행한 것은 아니다.
- 각 worker는 ai_env에서 exit 0, 최종 exit 2는 REVIEW다. 설정 전·해제 후 GPU 스냅샷 기준 19:30:05–19:57:55, **27분 50초**다.

검산 코드: [review.py](review.py), 기계 판독 결과: [verification.json](verification.json), [review_metrics.json](review_metrics.json). `raw/`는 원본, `recomputed/`는 재계산 사본이다.

31,669표본 모두 메모리 6801 MHz·한도 70 W다. 전력은 21.06–69.24 W, 온도는 34–70°C다. 순간 SW Power Cap·SW/HW thermal 활성 표본은 0이고 thermal 누적 증가도 0이다. 조회 요청 50 ms에 실제 간격 중앙값은 52–53 ms, 전체 최대는 72 ms다. 1680블록 모두 호스트 측정 경계 안에 표본이 있다. 이 표본은 연속 관측이나 커널이 실제 실행되는 동안의 유효 주파수 측정을 대신하지 않는다.

시간 기준은 모두 기존 5% 이내다. 처음/마지막 750의 30개 조건·방식별 두 round 중앙값 비교에서도 변화 절댓값 최대 **0.1556%**다. 이는 이번 연속 실행의 앞뒤 반복 결과이며 다른 날짜·독립 세션의 재현성 보장은 아니다.

각 단계의 `-lgc` 값은 750/780/810/750, `-lmc`는 6801로 정확히 기록됐다. 두 해제 명령은 성공했으며 직후 SM 1680·메모리 7001 MHz가 관측돼 고정값에서 벗어났다. 세부 표는 [stage_metrics.csv](stage_metrics.csv)에 있다.

## 클럭을 올렸지만 시간은 거의 같음

아래는 prealloc의 두 round 중앙값을 다시 중앙값으로 합친 값이다.

| 조건 | 750 MHz | 780 MHz | 810 MHz |
|---|---:|---:|---:|
| 4096³ FP32 | 18.6090 ms | 18.6023 ms | 18.6043 ms |
| 4096³ FP16 | 3.66890 ms | 3.66802 ms | 3.66908 ms |
| (1888,832,632) FP32 | 380.498 µs | 380.202 µs | 380.621 µs |
| 64³ FP16 | 6.23658 µs | 6.23299 µs | 6.23739 µs |

750→810은 요청 주파수 8% 증가지만 30개 조건·방식 조합의 시간 변화 절댓값은 최대 **0.4865%**다. 따라서 이번 자료에서 810의 일관된 성능 이득은 확인되지 않았다. 모든 형상이 코어 주파수에 반비례해야 하는 것은 아니므로 이 사실만으로 측정 오류나 메모리 병목을 확정하지 않는다.

설정 명령과 단계 표본이 대응하고, 결과 네 파일은 서로 다른 hash이며 1680블록 타임스탬프도 모두 다르다. 기존 Timer는 event 시간/실제 GEMM 횟수로 계산하고 SM MHz로 보정하지 않는다. 저장된 호스트 시간의 같은 분모도 재검산했다. 1680블록에서 호스트/event 시간 차이 절댓값은 최대 0.0178%로, 호스트 시간에서도 같은 평탄한 경향이다. 호스트 측정과 CUDA event가 같은 블록을 둘러싸므로 이를 독립적인 커널 시간 계측으로 해석하지 않는다.

전수 표: [clock_sensitivity.csv](clock_sensitivity.csv), [host_time_checks.csv](host_time_checks.csv).

## 일반 torch.mm, prealloc, Graph

810 MHz에서 두 round를 합친 결과다. allocate는 출력 할당을 포함한 `torch.mm(A,B)`이고, prealloc은 `torch.mm(A,B,out=C)`다. Graph는 기존 저장된 묶음의 replay 시간/GEMM 횟수다.

| 조건 | allocate | prealloc | Graph | Graph의 prealloc 대비 시간 변화 |
|---|---:|---:|---:|---:|
| 64³ FP16 | 6.236 µs | 6.237 µs | 4.614 µs | −26.03% |
| 64³ FP32 | 16.356 µs | 16.359 µs | 13.442 µs | −17.83% |
| (1888,832,632) FP16 | 96.558 µs | 96.544 µs | 94.953 µs | −1.65% |
| 4096³ FP32 | 18.6153 ms | 18.6043 ms | 18.6034 ms | −0.005% |

allocate/prealloc 차이 절댓값은 810의 10조건에서 최대 **0.0728%**, 네 단계의 40조건에서 최대 **0.1985%**다. 예열·반복된 입력과 캐싱 할당자를 쓰는 이번 블록 프로토콜에서는 작은 차이라는 근거다. 모든 호출에서 새 cudaMalloc을 강제한 실험이나, 개별 호출의 Python 지연 측정은 아니다. 기존 10,000조건 전체에서 allocate를 생략할 근거로 확대하지 않는다. Graph 차이도 순수 CPU 제출 대기량으로 환산하지 않는다.

전수 표: [mode_comparison.csv](mode_comparison.csv). 원래 round별 80묶음은 `raw/.../paired_metrics.csv`에 보존했다.

## REVIEW의 남은 사유와 다음 검증

각 약 416초 구간에서 누적 SW Power Capping은 약 367초씩 증가했다. 별도 `nvidia-smi -q`의 시작/끝 카운터도 이에 대응한다. 순간 활성 표본은 모두 0인데 timed 블록 130개에서 누적 증가가 있으며, 내부 표본 간격보다 증가량이 큰 사례가 남는다. 예를 들어 처음 750 단계의 한 prealloc 블록에서 52 ms 표본 간격 동안 499,840 µs 증가했다. 카운터를 제한 시간 비율로 해석하거나 드라이버 버그·제한 완전 부재로 확정하지 않는다.

다음 권고는 대규모 수집보다 **750/810의 소수 대표 GEMM에서 커널 실행 시간·SM cycle 기반 주파수·실제 커널 경로를 함께 확인하는 것**이다. 큰 FP32/FP16과 이전 900에서 문제가 난 FP32를 우선 대상으로 삼을 수 있다. 이후 유지 후보에서 더 넓은 파일럿을 확인한다. 이번 검토는 후속 GPU 실행이나 새 패키지 생성을 수행하지 않았다.

Nsight Compute 진단을 만든다면 외부 고정값을 비교하므로 `--clock-control none`을 명시해야 한다. 기본 클럭 제어·캐시 정책·replay가 비교 조건을 바꿀 수 있고, 프로파일 중 호스트/CUDA event 시간에는 도구 비용도 들어간다. 따라서 무프로파일 결과를 기준으로 보존하고 profiler 지표는 진단용으로 구분한다. 근거: [NVIDIA Nsight Compute Profiling Guide](https://docs.nvidia.com/nsight-compute/ProfilingGuide/#clock-control), [측정 시간과 도구 차이](https://docs.nvidia.com/nsight-compute/ProfilingGuide/#workload-durations).
