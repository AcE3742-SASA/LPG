# 레이어 명세 재검토: PyTorch 실행 경로와 검증 범위

2026-10-03. **명세 v1은 검증 완료 상태가 아니다.** 데이터 대응표와 목록의 정적 검사는 통과했지만, 구현 선택의 타당성, GPU 정확성, 실행 경로 및 예측 성능은 검증되지 않았다. 이번에는 제출본, 현재 명세와 생성 코드, PyTorch 공식 소스와 NVIDIA 문서를 대조했다. 여러 관점에서 검토했으며 독립된 외부 검토를 받았다는 뜻은 아니다.

검토 대상은 [명세 v1](../layer_spec_v1_2026-10-02/README.md), [후보 생성기](../layer_spec_v1_2026-10-02/build_plan.py), [기존 GEMM 측정 코드](../../gpu_sweep_v6/measure.py), [실제 제출본](/Users/studyhard/Claude/AcEVault/sources/휴먼테크_제출본_2026-09-22.md)이다. v1 파일과 해시, 기존 자료와 잠금 시험을 그대로 보존했다. 새 레이어 실행 코드는 구현하지 않았고 GPU 실행도 없다.

## PyTorch 사용 여부

기존 GEMM 측정은 이미 `torch.mm`을 사용한다. 새 레이어 후보도 `torch.mm`, `F.gelu`, `F.unfold`와 tensor 변환을 연결하는 방식이다. 우리가 작성하는 부분은 호출 순서와 측정 코드이며, GEMM이나 GELU의 CUDA 커널을 직접 작성하는 안이 아니다. NVIDIA CUDA에서 행렬곱의 cuBLAS 계열 호출은 [PyTorch 공식 소스](https://github.com/pytorch/pytorch/blob/v2.14.0/aten/src/ATen/native/cuda/Blas.cpp)에서 확인했다. 실제 장비의 선택 커널과 성능은 별도 확인 대상이다.

그러나 PyTorch 연산을 사용한다는 사실만으로 표준 `nn.Conv2d`와 같은 실행 경로가 되지는 않는다. v1의 3×3 Conv는 펼친 patch 행렬을 만들고 다시 배치 복사를 거쳐 GEMM을 실행한다. [PyTorch Unfold 문서](https://docs.pytorch.org/docs/2.14/generated/torch.nn.Unfold.html)는 patch 추출과 행렬곱의 수학적 대응을 설명한다. [NVIDIA 합성곱 문서](https://docs.nvidia.com/deeplearning/performance/dl-performance-convolutional/index.html)는 implicit GEMM이 펼친 행렬을 메모리에 만들지 않는다고 설명한다. 따라서 두 구현의 시간이나 메모리 사용량이 같다고 가정할 수 없다. 어느 쪽이 얼마나 빠른지는 아직 측정하지 않았다.

## 검토에서 남은 문제

| 항목 | 확인된 사실과 필요한 보완 |
|---|---|
| 예측 대상 | 제출본은 n×n Conv를 explicit GEMM으로 한정한다. v1은 1×1 Conv에도 입력과 출력 복사를 넣는다. 이 경로의 예측 결과를 표준 PyTorch Conv 전체에 일반화할 수 없다. 표준 레이어의 실제 시간까지 목표로 할지 먼저 구분해야 한다. |
| 구현과 비교 기준 | Linear/FFN은 weight를 `[K,N]` contiguous로 미리 준비한다. 표준 Linear의 weight 배치와 실행 계약이 같다고 확인한 것은 아니다. 동일 입력과 원래 weight로 표준 `nn.Linear`/GELU/`nn.Conv2d`와 결과를 대조하고, 성능을 비교할 경우 준비 비용, 입출력 배치와 정밀도 설정을 기록해야 한다. |
| Graph 해석 | ordinary는 결과를 할당하는 GEMM, Graph는 사전 할당 `out` GEMM이다. 두 시간의 차이에는 호출 방식과 버퍼 정책의 차이도 포함된다. 순수 Graph 효과로 해석하면 안 된다. probe로 반복 묶음을 정하는 정책도 실측과 준비 비용을 요구하며 아직 확정되지 않았다. |
| 표본과 학습 분할 | 50그룹, 30/10/10과 C 초기 20%는 후보 선택이다. 재확인한 구성 GEMM 242형상은 모두 M/N/K가 8의 배수다. 인접 중복을 막았다는 검사만으로 형상 대표성, 꼬리 처리나 표본 수의 충분성이 검증되지는 않는다. |
| 평가 기준 | 목표 오차, 모델과 seed, 탐색 예산 및 같은 목표 오차까지의 비용 비교는 미확정이다. 이 기준이 있어야 단순 보정·직접 예측과 공정하게 비교하고 자료량의 충분성을 판단할 수 있다. |

Linear는 GEMM 한 번이고, v1에서 여러 GEMM을 연결하는 종류는 FFN뿐이다. Linear를 측정 경계의 대조군으로 쓰는 것은 가능하지만 네 종류 모두가 여러 GEMM의 조립을 검증한다고 표현하면 안 된다.

## 다음 검토의 통과 기준

1. **연구 대상 검토:** explicit 분해 구현과 표준 PyTorch 레이어의 질문을 구분한다. 실제 표준 레이어 시간까지 주장하려면 표준 API의 실측 평가가 필요하다. 제출본의 explicit Conv 범위를 변경하는 것은 별도 제안이다.
2. **구현 계약 검토:** 각 호출의 shape, stride, weight 방향, 실제 복사, 준비 비용과 시간 경계를 대조한다. 표준 API와 수치 결과를 비교할 계약을 정하고, 불필요한 복사로만 보정 효과가 커지는지 확인할 대조 조건을 정한다.
3. **평가 설계 검토:** 형상 범위와 표본 수의 근거, A/C 분리, 비교 모델, 목표 오차와 비용 장부를 고정한다. 기존 및 새 시험 시간으로 후보 목록을 재설계하지 않는다.
4. **GPU 예비 검증:** 승인된 train 대표 조건에서 수치 정확성, 실제 실행 경로, Graph capture와 메모리, 회차 안정성을 확인한다. 기준을 통과한 뒤 실행 명세와 본측정 목록을 동결한다.

이번에 확인한 것은 v1 release 해시 일치, 50그룹의 30/10/10 분할, 242개의 고유 GEMM 형상과 모든 차원의 8배수 여부다. 제출 범위와 API 문서 대조에서는 위 보완 항목이 남았다. 네 검토를 모두 통과했다거나 명세가 확정됐다는 결론은 내리지 않는다.
