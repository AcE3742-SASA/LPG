# GPU 공식 사양과 720 MHz 측정값의 정합성 검토

2026-09-22

현재 720 MHz 결과는 정밀도와 클럭을 맞춰 계산한 이론 범위 안에 있다. 다만 FP32 6.14 TFLOP/s는 시험한 CUTLASS 커널의 기준선으로 사용해야 하며 GPU 전체의 최대 성능으로 확정할 수 없다. 이전 750 MHz의 FP16 결과에는 새로 확인한 상한 비교 불일치가 있어 검토 대상으로 남긴다. 기존 실행 검사 PASS와 원자료는 바꾸지 않았다.

## 1. 비교 기준

대상은 NVIDIA RTX 4000 SFF Ada Generation이다. SFF가 없는 RTX 4000 Ada나 GeForce RTX 40 제품과 구분한다. NVIDIA의 [제품 데이터시트](https://www.nvidia.com/content/dam/en-zz/Solutions/design-visualization/quadro-product-literature/proviz-rtx-4000-sff-ada-datasheet-2616456-web-1.pdf) 2쪽은 CUDA 코어 6,144개, Tensor Core 192개, 160-bit 메모리 버스, 대역폭 280 GB/s와 전력 70 W를 제시한다. FP32 19.2 TFLOP/s는 GPU Boost 기준이고 Tensor 306.8 TFLOPS는 희소 FP8 수치다. 후자를 dense FP16 실측의 분모로 바로 쓰지 않는다.

[전문가용 Ada 아키텍처 백서](https://images.nvidia.com/aem-dam/en-zz/Solutions/technologies/NVIDIA-ADA-GPU-PROVIZ-Architecture-Whitepaper_1.1.pdf) 28–30쪽의 코어 수, 클럭과 정밀도별 처리율을 대조했다. dense FP16은 희소 FP8의 1/4이며, FP32 누산에서도 전문가용 경로의 같은 처리율을 제시한다. 이 관계를 적용하면 제품의 boost 기준 dense FP16은 약 76.7 TFLOP/s다. 이것은 RTX 4000 SFF 데이터시트에 별도 표기된 값이 아니라 아키텍처 관계로 환산한 값이다. GeForce의 FP32 누산 제한을 그대로 가져오지 않았다.

720 MHz에 대한 계산은 다음과 같다. FMA는 곱셈과 덧셈의 2 FLOP로 센다.

- FP32: 6,144 × 2 × 720×10⁶ = 8.84736 TFLOP/s.
- dense FP16 Tensor Core: 192 × 256 FLOP/clock × 720×10⁶ = 35.38944 TFLOP/s.
- 메모리: 280 × 6801/7001 ≈ 272.0 GB/s. 7001 MHz는 저장된 장치 정보의 최대 메모리 클럭이고 6801 MHz는 이번 관측값이다. 같은 전송 방식에서 대역폭이 메모리 클럭에 비례한다는 계산 기준이다. ECC는 저장된 장치 정보에서 비활성이었다.

연산 상한은 기록된 SM 클럭이 연산 중 유효 클럭을 대표하고 위의 전문가용 Ada 처리율이 해당 SKU에 적용된다는 전제다. [nvidia-smi 문서](https://docs.nvidia.com/deploy/nvidia-smi/index.html)는 클럭 조회값과 설정 기능을 설명하지만 센서 표본만으로 전체 timed 구간의 연속 유효 클럭을 검증한 것은 아니다.

## 2. 현재 결과의 판정

| 항목 | 공식 사양 또는 환산값 | 이번 클럭의 계산 기준 | 실측 | 계산 기준 대비 |
|---|---:|---:|---:|---:|
| FP32 SIMT | 19.2 TFLOP/s | 8.85 TFLOP/s | 6.14 TFLOP/s | 69.4% |
| dense FP16, FP32 누산 | 약 76.7 TFLOP/s | 35.39 TFLOP/s | 35.02 TFLOP/s | 98.9% |
| 메모리 대역폭 | 280 GB/s | 약 272.0 GB/s | 262.3 GB/s | 96.4% |

세 값 모두 비교 기준을 넘지 않는다. FP32의 미달분만으로 측정 오류라고 판정할 근거는 없지만, 69.4%라는 값이 최대 성능 포화를 입증하지도 않는다. FP16은 계산 상한에 가까우며 대역폭도 현재 메모리 클럭의 범위 안에 있다. 대역폭은 BabelStream Dot의 논리적 읽기량 기준으로, 실제 DRAM 트래픽 카운터 값과 동일시하지 않는다.

기존 검산과 함께 보면 수치 계산, 설정된 정확성 검사와 같은 세션 내 반복성은 통과했다. 720 MHz 최고 커널의 원본 CSV 5개씩에서 2MNK/Runtime을 다시 계산해 FP32 6.1399075967695325, FP16 35.01587569498772 TFLOP/s 중앙값이 기존 집계와 일치함을 확인했다. 전체 조건의 범위/중앙값 최대는 0.44%다. 누적 전력 제한 카운터의 해석 미해결 상태는 유지한다.

## 3. 예비 GEMM 자료와 대조한 천장의 대표성

200형상의 세 회차 집계 1,200조합을 대조했다. FP32 최고값은 (4096,4096,4096) Graph의 6.45 TFLOP/s로 계산 상한의 72.9%다. 이는 CUTLASS 기준 6.14보다 5.0% 높다. FP32 600조합 중 15조합이 해당 CUTLASS 기준을 넘었다. 모든 FP32 조합은 계산한 하드웨어 상한 안에 있다.

FP16 최고값은 같은 형상 Graph의 32.61 TFLOP/s로 계산 상한의 92.2%, CUTLASS 기준의 93.1%다. FP16 600조합 중 CUTLASS 기준을 넘는 것은 없었다.

따라서 6.14는 현재 시험한 CUTLASS 커널들의 경험적 기준선이다. 라이브러리와 배치, 반복 및 캐시 정책이 다른 예비 GEMM이 이를 넘었다고 바로 오류가 되는 것은 아니다. 반대로 이 값이 모든 GEMM의 최대 성능을 대표한다고 쓸 수는 없다. 경험적 효율 η를 1 이하로 강제하지 않는 현재 계획은 유지한다. 관측한 6.45로 천장을 임의 교체하지 않고, 더 넓은 천장 후보를 정할 때에는 동일한 프로토콜과 독립 자료를 사용한다.

## 4. 이전 750 MHz 자료에서 발견한 불일치

같은 계산에서 750 MHz dense FP16 상한은 36.864 TFLOP/s다. 보존된 실측 40.26 TFLOP/s는 상한의 109.2%로 약 9.2% 높다. FP32 7.05는 9.216 TFLOP/s의 76.5%이고, 대역폭 263.0 GB/s도 메모리 기준 범위 안에 있다.

FP16 최고 커널의 다섯 원본 CSV를 다시 확인했다. 모두 dense GEMM, FP32 누산, batch=1, split-K=1, 검증 passed이며 2MNK/Runtime 중앙값은 40.25911391619639 TFLOP/s로 재현된다. CUTLASS의 별도 FLOPs 필드가 포함한 epilogue 산술량 차이는 16384³에서 0.0061%에 불과하고, 이번 계산은 처음부터 2MNK를 사용했으므로 9.2% 초과를 설명하지 못한다. 해당 처리율을 이 계산 모델로 만족하려면 최소 약 819 MHz의 유효 연산 클럭이 필요하지만 센서는 750 MHz로 기록됐다.

이것은 이전의 파일 검산 실패가 아니라 사양, 유효 클럭, 타이머 또는 실행 경로 전제의 추가 검토 사유다. 어느 항이 원인인지 현 자료만으로 단정하지 않는다. 750 MHz FP16을 검증된 물리적 천장으로 인용하는 판단은 보류한다. 새 GPU 측정은 수행하지 않았다.

## 5. 초록에 사용할 수 있는 판정 문장

“720 MHz에서 측정한 FP32와 dense FP16 Tensor Core 처리율은 아키텍처와 설정 클럭으로 계산한 이론 성능의 각각 69.4%와 98.9%였으며, BabelStream Dot 대역폭은 메모리 클럭을 반영한 기준의 96.4%였다. 다만 FP32의 일부 예비 GEMM이 CUTLASS 측정값을 상회하여, 이를 시험한 커널 경로의 경험적 기준선으로 사용하였다.”

이 문장은 물리적 범위 비교이며 모든 측정 문제의 해결이나 최대 성능 확보를 뜻하지 않는다. v8 원고는 보존했다. [계산과 입력 해시](spec_consistency.json), [재현 코드](check_spec_consistency.py), [720 MHz 기존 보고서](report.md)를 함께 참고한다.
