# 낮은 클럭 후보 진단 패키지 검증

`clock_lower_v1`을 준비했다. 실제 GPU 실행은 하지 않았고 최종 클럭과 본수집은 미확정이다. 배포 ZIP은 `../../clock_lower_2026-09-20_v1.zip`이다.

750→780→810→750 MHz 네 단계, 메모리 6801 MHz, 기존 한도 70 W, 조회 50 ms다. 900 MHz에서 문제가 있었던 FP32 네 조건과 기존 진단 네 조건, 64³ FP16/FP32 두 조건을 포함한다. 단계마다 동일 입력의 allocate/prealloc/Graph를 두 round 측정해 총 240측정·1680블록·80개의 세 방식 묶음이다. 코어 후보는 사용자의 지원 목록에서 고른 실험값이며 유지 가능하거나 최대라고 주장하지 않는다.

기존 v6의 Timer·GEMM·정확성 함수와 clock_audit worker를 그대로 재사용한다. 원본 프로토콜의 예열·안정화·블록·5% 기준은 유지하고 조건 목록·방식 순서·Graph 묶음·조회 단계만 프로세스 안에서 임시 연결한다. 원래 42개 의존 소스는 해시로 변경 없음을 확인했다. 선택한 10개 형상/dtype의 seed·Graph 묶음·정확성 범위는 실제 fixed_pilot 결과의 40개 prealloc/Graph 기록과 일치했다. 출력 할당 경로는 기존 v6 구현을 재사용하며 새 GPU 결과는 아직 없다.

새 회귀 검사 9개, 재사용 steps 10·fixed 8·v6 10·audit 10, 합계 47개가 통과했다. 새 검사에는 세 방식 누락·중복, 잘못된 분모·seed·Graph·정확성 범위·환경, 관측 누락·목표 미유지·전력 제한, counter 증가와 시간/클럭 판정 분리, round와 앞뒤 750 차이, 소스 변조, 설정/worker/복원 실패, 사전 진입 실패 및 중단 후 복원이 포함된다. 가짜 실행기로 실제 Bash launcher의 exit 2 보존과 SIGINT 뒤 자식 정리 완료 후 ZIP 생성도 확인했다. 로컬 합성 PASS는 후보 클럭의 GPU 유지나 지연 측정 PASS를 뜻하지 않는다.

Python AST·Bash 구문·의존성 verify가 통과했고 7개 배포 파일의 ZIP CRC·바이트 일치도 확인했다. ZIP SHA-256은 `e74b87a32535b5a0596642c5d97e0f4d6f29e3640fd6e9ba93acd48b5b1f5fb1`이다. 재현 가능한 검사 명령과 결과는 [checks.json](checks.json), 파일 해시와 배포 대조는 [validation.json](validation.json)에 있다.

시간·실제 관측 클럭, 누적 카운터 한계를 별도 판정한다. 전체 단계에서 활성 표본이 한 번이라도 나오면 블록별 카운터 이상이 숨는 기존 집계 한계를 보완했다. 기존 소스를 고치거나 표식을 삭제하지 않고 새 분석에 블록별 증가·간격 초과 표식을 추가했다. 이 값은 제한 시간 비율이 아니다. PASS여도 full HOLD·최종 클럭 null을 유지하며 대표 조건의 allocate 비교를 10,000조건 전수 생략 근거로 자동 처리하지 않는다.
