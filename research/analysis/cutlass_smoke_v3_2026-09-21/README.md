# v2 사전 검사 오류와 v3 수정

사용자 제공 `cutlass_780_smoke_v2.Mud6Ib.tar.gz`의 10개 파일을 확인했다. 두 설정 로그에는 SM 780 MHz·메모리 6801 MHz 고정 성공이 기록되어 있지만, 설정 직후 `fp32_simt.before.csv`는 `210, 405, 70.00`이다. v2의 사전 검사에서 이 값을 목표 클록과 즉시 일치해야 한다고 요구해 종료코드 1로 중단했다. 프로파일러 명령 기록·실행 로그·CSV·부하 모니터가 없고 실행 흐름상 이 검사 다음에 프로파일러가 시작되므로 두 커널 모두 시작하지 않았다. 따라서 이번 자료에는 device 정확성 검증 결과나 성능값이 없다.

원본 runner SHA-256은 배포 v2와 같은 `0e96a77e8e295a672dafa5467789eb34e9205f28b8962755885e01cf8d99dbd6`이다. CUTLASS 바이너리 해시·체크아웃 커밋도 직전 자료와 같고, 소스 수정과 다른 계산 프로세스의 기록은 없다. 고정 명령 직후의 낮은 현재 클록만으로 부하 중 고정 실패를 판정한 것은 잘못된 검사 조건이다. [NVIDIA 문서](https://docs.nvidia.com/deploy/nvidia-smi/index.html#clocks-event-reasons)는 GPU가 쉬는 동안 클록이 Idle 상태로 내려갈 수 있음을 설명한다. 설정 적용/계측 시점의 지연과 무부하 상태 중 무엇이 이번 직후 값에 기여했는지는 별도로 측정하지 않았다. 이 값은 부하 중 780/6801 MHz가 유지된다는 증거도 아니다.

v3는 두 클록 설정 명령의 성공 여부를 계속 요구하고, 실행 전 스냅샷에서는 70 W만 검증한다. 실제 SM·메모리 클록은 기존과 같이 각 실행의 사용률>0 표본에서 780/6801 MHz·70 W인지 확인한다. `device` 기준 구현 비교·epsilon=0·8192³·두 커널·반복 조건·공유 GPU 잠금·오류 시 후속 중단·원자료 보존은 그대로다. 각 커널 시작 시 짧은 진행 메시지만 추가했다. 종료 시 클록 고정은 유지한다.

기존 테스트에 실제 업로드의 `210, 405, 70.00` 스냅샷을 연결했다. 이 상태에서는 실행을 허용하면서, 실제 부하의 SM 1470 MHz 또는 메모리 7001 MHz는 계속 거부하고 후속 커널을 막는 것을 확인했다. 전력 한도 65 W, 설정 명령 실패, 검증 실패, 다른 프로세스·공유 잠금 사용 중, 프로파일러 실패, 모니터 오류를 포함한 총 10개 로컬 대역 검사와 Bash 문법 검사가 통과했다. 이는 호스트 측 검사 동작의 확인이며 실제 GPU의 정확성·클록 유지는 새 실행 결과를 기다린다.

Ubuntu `/home/eu/cutlass_780_smoke_v3.sh`로 파일을 옮긴 뒤 기존 터미널에서 `bash /home/eu/cutlass_780_smoke_v3.sh`를 실행한다. 두 경로 PASS와 종료코드 0이 짧은 점검의 통과 기준이다. 성공·실패 시 마지막 tar.gz를 전달한다. 원본은 `raw_v2_failure/`, 파일별 해시는 `v2_failure.json`, 로컬 검사 결과는 `validation.json`에 보존했다. `python3 -B test_smoke.py`로 로컬 검사를 재현할 수 있다.
