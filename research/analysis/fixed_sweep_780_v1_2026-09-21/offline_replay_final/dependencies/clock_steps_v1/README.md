# 클럭 단계 진단 v1

900 MHz에서 확인한 안정성을 기준으로 1050, 1200, 1350 MHz의 실제 유지 여부와 시간을 비교한다. 메모리 목표는 6801 MHz이며 기존 전력 한도가 70 W인지 확인한다. 전력 한도를 바꾸는 명령은 실행하지 않는다. 최종 클럭 선정과 full 실행은 자동으로 진행하지 않는다.

압축을 풀어 `clock_steps_v1` 폴더를 `/home/eu/gemm-research/scripts/`에 둔다. 같은 위치에 기존 `clock_hold_v1`, `clock_audit_v1`, `gpu_sweep_v6` 폴더가 있어야 한다. 파일을 덮어쓰거나 라이브러리를 다시 설치할 필요는 없다.

```bash
bash /home/eu/gemm-research/scripts/clock_steps_v1/launch.sh
```

처음 `sudo` 암호를 요청할 수 있다. 기존 checked runner가 `ai_env`를 자동 활성화한다. 측정 Python은 일반 사용자로 실행되고 클럭 설정과 고정 해제만 `sudo`를 사용한다. 실행 중에는 이미 승인한 sudo 권한을 45초마다 비대화식으로 갱신하고, 끝나면 갱신 스레드를 종료한다. 예상 시간은 약 30~40분이며 아직 실제 GPU 실행 시간으로 확인한 값은 아니다. 다른 연구 측정과 동시에 실행하지 않는다.

시작할 때 `STEPS_DIR=...`가 표시된다. 이후 `STAGE 1/7`부터 `STAGE 7/7`까지 진행된다. 각 단계는 새 측정 프로세스를 사용하며 180초 예열 뒤 16개 측정을 수행한다. 단계 내부의 진행 상황은 `STEPS_DIR`에 생성되는 해당 단계의 `.log`에 남는다. 마지막의 `RESULT_ZIP=...` 파일을 검토용으로 반환한다. 실패하거나 Ctrl+C로 중단해도 종료한 로그를 포함한 ZIP 생성을 시도한다.

| 순서 | 코어 목표 | 조회 간격 | 목적 |
|---:|---:|---:|---|
| 1 | 900 MHz | 100 ms | 앞쪽 기준 |
| 2 | 900 MHz | 50 ms | 촘촘한 조회 비교 |
| 3 | 1050 MHz | 50 ms | 후보 검사 |
| 4 | 1200 MHz | 50 ms | 후보 검사 |
| 5 | 1350 MHz | 50 ms | 후보 검사 |
| 6 | 900 MHz | 50 ms | 뒤쪽 기준 |
| 7 | 900 MHz | 100 ms | 조회 간격·시간대 재비교 |

조건은 기존 (1888, 832, 632) FP16과 (392, 2776, 80) FP32에, v6 파일럿에서 이미 측정했던 4096³ FP16·FP32를 추가한다. 각 조건의 일반 prealloc과 CUDA Graph를 두 round씩 측정한다. 형상과 실행 방식의 순서를 두 번째 round에서 반대로 배치한다. 네 조건 × 두 방식 × 두 round × 일곱 단계로 총 112측정·784블록이다. 새로운 holdout 형상을 선정하지 않는다.

기존 v6의 타이머, 입력 생성, 정확성 검사, 3초 안정화, 100 ms 목표 블록, 7블록, 5% IQR·drift·round 기준을 재사용한다. Graph 묶음은 기존 진단의 29·56회와 4096³ 파일럿의 1·1회로 고정한다. seed는 각각 2241190505, 2739574071, 2125276676, 3255611920이다. `audit.worker`의 측정 코드는 변경하지 않고, 이 패키지의 실행 프로세스 안에서 조건 선택 함수와 조회 간격만 일시적으로 연결한다. 기존 파일은 바꾸지 않는다.

각 단계의 직전과 직후에는 측정 worker가 없는 10초 구간을 기록한다. 실험 처음과 끝에는 메모리만 6801 MHz로 유지하고 코어 고정을 해제한 10초 구간도 기록한다. 총 16구간이다. 여기서 유휴란 이 진단의 GEMM worker가 없다는 뜻이며 GNOME 등 데스크톱 GPU 클라이언트는 남을 수 있다. 관련 프로세스 조회 결과를 보존한다. 자동 코어 상태에서 GEMM 부하를 새로 측정하는 대조 실험은 포함하지 않는다.

클럭 설정 명령이 실패하면 중단한다. 명령은 수락됐지만 부하 중 코어가 목표보다 낮아진 경우는 REVIEW로 남기고 나머지 계획을 수집한다. 따라서 높은 후보가 실제로 유지되지 않아도 기록을 버리지 않는다. 메모리·전력 한도 차이, 측정 내부 표본 누락, 순간 전력·온도 제한 상태, 조회 중단과 비정상 간격, 블록·round 시간 변동도 검토 대상으로 남긴다. 100 ms 기준 단계에서는 이전처럼 표본이 없는 블록이 생길 수 있으며 이를 보간해 통과시키지 않는다.

전력 카운터는 별도로 분석한다. 단계별 부하와 10초 구간마다 첫/끝 telemetry 카운터, 해당 표본 시각 범위, 별도 `nvidia-smi -q` 전후 누적값을 저장한다. 카운터가 증가했는데 순간 활성 표본이 없으면 `increase_without_active_sample`로 표시한다. 감소나 N/A도 보존한다. 짧은 블록의 정확한 제한 비율을 계산하거나 드라이버 버그로 자동 판정하지 않는다. 더 잦은 조회가 센서 갱신 주기의 향상을 보증하지는 않는다. [NVIDIA 카운터 정의](https://docs.nvidia.com/deploy/nvidia-smi/#clock-event-reasons-counters)

900 MHz의 앞뒤 100/50 ms 비교 비율을 모두 저장한다. 이 비율에는 프로세스와 시간대·순서의 영향도 섞여 있어 순수 조회 비용으로 해석하지 않는다. 높은 후보는 각각 한 프로세스 안에서 두 round를 측정한다. 네 대표 조건의 결과로 모든 형상의 안정성이나 독립 세션 재현성을 인증하지 않는다. 최종 선정 후에는 해당 조건으로 전체 파일럿을 다시 검토해야 한다.

GPU UUID와 공유 잠금을 확인하고 다른 계산 작업이 있으면 설정 전에 중단한다. 설정 단계 진입 뒤 정상 종료, 측정 오류, 처리 가능한 SIGINT/SIGTERM에서는 코어와 메모리 고정 해제를 각각 시도한다. 두 명령과 복원 후 GPU 조회는 `restore.json`, `reset_graphics.json`, `reset_memory.json`, `gpu_after_restore.json`에 남는다. 기본 동작으로 고정을 해제하는 것이며 실행 전 수동 잠금값을 재적용하지는 않는다. 복원 실패는 FAIL이다. 최초 진입 검사 실패 시에는 기존 수동 설정을 건드리지 않는다. SIGKILL·전원 차단·sudo 권한 상실 시 복원을 보장할 수 없으므로 로그의 수동 복원 안내를 확인한다.

종료 코드는 0=수집·검사 PASS, 2=수집 완료 후 REVIEW, 1=실행·무결성·복원 FAIL, 130=중단이다. `summary.json`의 `counts`는 측정별 블록·표본 판정이며, 별도 단계·round·카운터·조회 비교 표식은 `flags`와 `analysis.json`에 모두 남는다. PASS여도 `full_sweep=HOLD`, `selected_clock_mhz=null`을 유지한다.

주요 출력은 `manifest.json`, `summary.json`, `report.md`, `analysis.json`, `clock_windows.json`, 각 단계의 원시 결과·환경·telemetry, 유휴 구간, 설정·복원 응답, `sudo_refresh.json`, 실행 로그와 소스 사본이다. `dependency_hashes.json`의 기존 28파일을 시작·worker 진입·종료 때 대조한다. 이 패키지에 대한 로컬 검증 기록은 별도 `analysis/clock_steps_v1_2026-09-20/`에 있다. 실제 GPU 측정과 후보 유지 여부는 사용자가 실행한 결과로 확인해야 한다.
