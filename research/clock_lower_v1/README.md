# 낮은 코어 클럭 후보와 세 실행 방식 진단

900 MHz 고정 파일럿에서 드러난 FP32 조건을 포함해 750/780/810 MHz 후보를 비교한다. 메모리는 6801 MHz로 설정하고 기존 전력 한도 70 W는 확인만 한다. 이번 결과는 후보를 검토하기 위한 자료이며 최종 클럭을 자동 선정하거나 10,000조건 본수집을 시작하지 않는다.

## 실행

ZIP의 `clock_lower_v1` 폴더를 Ubuntu `/home/eu/gemm-research/scripts/`에 둔다. 기존 `gpu_sweep_v6`, `clock_audit_v1`, `clock_hold_v1`, `clock_steps_v1`, `fixed_pilot_v1`은 같은 상위 폴더에 그대로 있어야 한다. 42개 의존 파일의 hash가 다르면 측정 전에 중단한다. 기존 설치를 다시 할 필요는 없다.

다음 한 명령을 일반 사용자 eu로 실행한다.

```bash
bash /home/eu/gemm-research/scripts/clock_lower_v1/launch.sh
```

처음 `DEPENDENCY CHECK: PASS`가 출력되고 sudo 비밀번호를 요청할 수 있다. 측정은 기존 checked runner가 `ai_env`를 활성화한 뒤 일반 사용자로 실행한다. sudo는 클럭 설정·해제에 사용하며 실행 중 기존 승인을 비대화식으로 갱신한다.

예상 시간은 약 30분, 계획 범위는 25~35분이다. 단계별 180초 예열과 약 60×4초 측정으로 네 단계 합계 약 28분을 예상한 값이며 실제 실행 시간은 달라질 수 있다. 단계별 worker 제한은 20분이다. 네 단계는 순차 실행한다.

```text
STAGE 1/4: s0_750_before
STAGE 2/4: s1_780
STAGE 3/4: s2_810
STAGE 4/4: s3_750_after
RESTORE: COMMANDS ACCEPTED
LOWER CLOCKS: PASS 또는 REVIEW; full remains HOLD
RESULT_ZIP=.../clock_lower_날짜_시간_식별자.zip
```

REVIEW는 수집 실패와 구분한다. exit 0은 자동 검토 표식 없음, exit 2는 REVIEW, exit 1은 실행·검증·복원 실패다. 중단 시에도 가능한 범위에서 복원과 결과 압축을 수행한다. 결과 ZIP 전체를 확인해야 후보를 판단할 수 있다. 기존 fixed_pilot 결과는 이번 ZIP에서 변경하지 않는다.

## 측정 구성

| 순서 | 코어 요청 | 메모리 요청 | 조회 간격 |
|---|---:|---:|---:|
| 처음 | 750 MHz | 6801 MHz | 50 ms |
| 두 번째 | 780 MHz | 6801 MHz | 50 ms |
| 세 번째 | 810 MHz | 6801 MHz | 50 ms |
| 마지막 재측정 | 750 MHz | 6801 MHz | 50 ms |

750은 이전 worker 전체 최저 관측값 810 MHz보다 여유를 둔 후보이고 780/810으로 위쪽 범위를 비교한다. 세 값은 사용자가 제공한 지원 목록에 있다. 설정 수락과 부하 중 유지는 아직 GPU에서 검증하지 않았고, 실제로 내려간 클럭을 다음 유지 가능 클럭의 증거로 사용하지 않는다. 825 MHz 이상은 이번 범위 밖이며 가장 높은 유지 가능 클럭을 찾는 실험이라고 주장하지 않는다.

각 단계는 아래 10형상/dtype 조합을 출력 할당·prealloc·Graph, 두 round씩 측정한다. 총 240측정·1680블록·세 방식 비교 80묶음이다. 10개 조합은 기존에 관측한 개발 조건이며 새 holdout을 열지 않는다.

| M,N,K | dtype | 선택 이유 | Graph당 GEMM |
|---|---|---|---:|
| 1888,832,632 | FP32 | 900 MHz 파일럿에서 REVIEW | 9 |
| 3216,520,776 | FP32 | 900 MHz 파일럿에서 REVIEW | 4 |
| 1016,2048,504 | FP32 | 900 MHz 파일럿에서 REVIEW | 6 |
| 1999,646,425 | FP32 | 900 MHz 파일럿에서 REVIEW | 8 |
| 1888,832,632 | FP16 | 기존 집중 진단 | 29 |
| 392,2776,80 | FP32 | 기존 집중 진단 | 56 |
| 4096,4096,4096 | FP16 | 기존 큰 GEMM 대조 | 1 |
| 4096,4096,4096 | FP32 | 기존 큰 GEMM 대조 | 1 |
| 64,64,64 | FP16 | 작은 GEMM의 실행 방식 비교 | 64 |
| 64,64,64 | FP32 | 작은 GEMM의 실행 방식 비교 | 64 |

`allocate`는 기존 v6의 `torch.mm(A,B)` 호출이고 `prealloc`은 `torch.mm(A,B,out=C)`, `graph`는 같은 prealloc 호출을 고정 묶음으로 캡처한 replay다. 입력 seed는 형상·dtype에만 의존해 방식·round·단계 간 동일하다. Graph 묶음과 정확성 범위는 기존 fixed_pilot의 저장 설정과 일치시킨다. 매 단계 프로세스는 새로 시작하지만 같은 단계 안에서 세 방식은 같은 프로세스에서 실행된다. 형상별로 세 방식의 시작 위치를 순환시키고 다음 round에서 형상·방식 순서를 모두 뒤집는다.

PyTorch는 캐싱 할당자를 사용하므로 allocate를 매 호출 새 cudaMalloc 실험이라고 부르지 않는다. 캐시를 강제로 비우거나 새 할당자를 설치하지 않는다. 기존 함수가 워밍업 후 결과 텐서를 교체하는 동작을 그대로 사용한다. [PyTorch 메모리 관리 문서](https://docs.pytorch.org/docs/2.14/notes/cuda.html#memory-management).

입력 생성은 시간 측정 밖에 있고 allocate의 출력 생성 호출은 event 블록 안에 있다. CUDA event 블록에는 노출된 제출 간격이 포함될 수 있다. 두 방식의 차이는 순수 할당 비용이나 CPU 제출 대기로 인과 분해하지 않는다. `paired_metrics.csv`에는 세 시간을 별도 열로 보존한다. 이번 대표 조건 결과만으로 기존 10,000조건의 allocate 전수 수집을 자동 생략하지 않는다.

## 기준과 기록

기존 v6 Timer·GEMM·정확성 함수, 프로세스별 180초 예열, 조건별 3000 event ms 안정화, 약 100 ms 블록 7개, 상대 IQR·drift·round 차이 5%를 그대로 쓴다. 전체 출력 비교는 48측정, 256원소 표본 비교는 192측정이다. 출력 할당 경로에도 동일한 정확성 검사를 적용한다.

실제 worker 전체 표본과 timed 호스트 경계 내부 표본을 나눠 검사한다. 요청 코어·메모리·전력 한도와 다르거나 순간 전력/열 제한이 관측되면 클럭/시간 검토 표식을 남긴다. 내부 표본 없는 블록, 관측 누락, 느린 조회 간격도 보존한다. 50 ms 요청은 연속 관측이나 센서 해상도를 보증하지 않는다.

NVIDIA는 SW Power Cap을 전력 소비 때문에 요청 클럭 아래로 낮추는 상태로 설명한다. 따라서 설정 명령의 성공만으로 목표 유지가 증명되지는 않으며 부하 중 관측을 따로 판정한다. [NVIDIA nvidia-smi 문서](https://docs.nvidia.com/deploy/nvidia-smi/).

누적 전력/열 카운터는 별도 기록한다. 전체 단계에서 순간 비활성인데 누적값이 증가하는 경우 외에, 블록 내부 표본 사이에서도 비활성 중 증가·관측 간격보다 큰 증가량을 보존한다. 이런 표식은 시간/관측 클럭 판정과 따로 표시하며 제한 시간 비율로 환산하지 않는다. 과거 카운터 문제는 미해결로 남긴다. 이번에 자동 표식이 없다고 과거 문제까지 해결된 것으로 처리하지 않는다.

`repeat_750.csv`는 처음과 마지막 750 MHz 단계의 방식별 round 중앙값을 비교하며 5%를 넘으면 REVIEW다. 다른 후보와의 차이 및 앞뒤 차이에는 프로세스·순서·시간대 효과가 포함되고 순수 클럭 효과나 독립 세션 재현성으로 해석하지 않는다.

원본·manifest·모든 소스 hash·환경·프로세스·블록·텔레메트리·복원·종료 코드와 분석을 ZIP에 보존한다. `analysis.json`과 `clock_windows.json`이 전체 근거이고, `measurements.csv`, `review_queue.csv`, `paired_metrics.csv`, `repeat_750.csv`, `report.md`로 요약한다. 설정·worker 실패에서는 완료된 단계 원자료와 FAIL 요약을 보존하고 자동 분석·후속 부하는 중단한다.

## 종료와 범위

대상 UUID, 공유 GPU 잠금, 다른 GPU 작업, 70 W 검사를 통과한 뒤 클럭을 설정한다. 설정 실패·worker 오류·처리 가능한 중단·정상 종료에서 worker 종료를 확인하고 잠금을 유지한 채 코어와 메모리 고정 해제를 각각 시도한다. 복원은 기존 수동값으로 되돌리는 것이 아니라 기본 자동 클럭으로 해제한다. 사전 진입 실패라면 기존 설정을 건드리지 않는다. 전원 차단이나 SIGKILL에서는 종료 처리가 실행되지 않을 수 있다.

이번 진단에는 새 Nsight 캡처, 자동 코어 GEMM 대조, 유휴 카운터 반복 진단, 학습, 전체 24형상 재검증, 10,000조건 본수집이 없다. 결과를 먼저 검토하고 유지 가능한 후보가 있으면 그 후보로 전체 파일럿을 준비한다. PASS여도 `selected_clock_mhz=null`, `full_sweep=HOLD`다.

로컬 검증은 합성 데이터·가짜 명령으로 수행한다. 실제 GPU에서 후보 클럭 유지, 출력 할당 경로의 지연, 정확성 검사가 통과하는지는 이번 실행 결과로 확인해야 한다.
