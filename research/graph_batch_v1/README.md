# Graph 묶음 수 비교 v1

64³ FP16·FP32, 128³ FP16에서 한 Graph에 GEMM을 16·32·64·128회 담는다. Nsight를 끈 CUDA Event 시간으로 묶음 수를 늘릴 때 GEMM당 시간이 수렴하는지 확인한다. 기존 v5와 timing audit 원자료는 보존하며 이 패키지는 본측정·학습 정답을 확정하지 않는다.

## 실행

ZIP을 풀어 나온 `graph_batch_v1` 폴더를 GPU 컴퓨터의 `/home/eu/gemm-research/scripts/`에 놓는다. 그 옆에는 기존 `gpu_sweep` v5가 있어야 한다. `timing_audit_v4` 폴더는 실행에 필요하지 않다.

```bash
bash /home/eu/gemm-research/scripts/graph_batch_v1/launch.sh
```

정상 시작은 `GRAPH_BATCH_DIR=...`, `V5 SOURCE CHECK: PASS`, `ENV CHECK: PASS`, `Starting round 1/4`다. 각 round의 상세 진행은 표시된 `round_0.log`~`round_3.log`에 남는다. 매번 첫 3분은 예열하므로 조건 완료 출력이 없다.

**계획용 예상 16~20분.** 새 프로세스 4개의 초기 예열만 12분이며, 48개 조건의 안정화·측정은 약 3분 이상이다. 패키지의 GPU 실측 시간은 아직 없다. 터미널을 유지하고 다른 GPU 계산을 함께 돌리지 않는다.

완료 후 `COLLECTION COMPLETE`, `STABILITY: PASS` 또는 `REVIEW`, `BATCH CANDIDATES: ...`, `RESULT_ZIP=...`가 나온다. 결과 ZIP을 전달한다. `EXPERIMENT: PASS`는 수집 프로그램의 정상 종료이며 수렴·본측정 승인과 별개다. `null` 후보는 자동 선정하지 못했다는 뜻이다. 실패 시에도 오류 로그와 종료 코드를 ZIP으로 보존한다. 중단된 실행은 재사용하지 않고 새 출력 폴더에서 시작한다.

## 고정 조건과 변경점

v5의 입력 seed, 정밀도 설정, 출력 사전 할당, 정확성 검사, Timer.block/prepare/run을 그대로 재사용한다. 초기 예열 180초, 조건별 관측 event 안정화 3초, 블록 목표 100 ms, 7블록, IQR·첫/끝 drift·실행 간 변동 5% 기준을 유지한다. 첫 블록과 불리한 결과를 삭제하지 않는다.

Graph 캡처만 기존 적응 묶음 수 대신 **정확히 지정한 GEMM 횟수**를 사용한다. `gemms_per_replay`는 GEMM 수이며 CUDA 커널 노드 수가 아니다. FP32 하나의 GEMM은 보조 커널을 포함할 수 있다. side stream에서 3회 준비 후 캡처하고 첫 replay·동기화를 끝낸 뒤 기존 안정화와 측정을 진행한다. 캡처·입출력 생성·정확성 검사는 측정 구간 밖이다. [PyTorch 2.14 Graph 문서](https://docs.pytorch.org/docs/2.14/notes/cuda.html#cuda-graphs)의 stream 동기화와 tensor 수명 규칙을 따른다.

한 프로세스의 같은 형상·정밀도에서는 입력/출력 tensor와 주소를 네 묶음 수에 걸쳐 그대로 유지한다. 입력 내용의 seed는 모든 묶음 수와 프로세스에서 같다. 같은 입력을 반복하는 조건이므로 캐시가 차가운 단발 호출 시간으로 해석하지 않는다.

```
GEMM당 시간 = 블록 CUDA Event 시간 / (Graph replay 수 × GEMMs per replay)
```

replay 수는 각 조건에서 기존 알고리즘으로 보정하므로 조건마다 다를 수 있다. 실제 횟수, 정규화 분모, raw 7블록, 안정화 기록, seed, tensor 주소를 저장하고 분석 시 대조한다. Graph 내부 GPU 간격과 보조 작업도 포함하며 순수 커널 시간이라고 부르지 않는다.

3조건 × 4묶음 × 새 프로세스 4회 = **48개 측정, 336블록**이다. 프로세스마다 아래 순서로 묶음을 실행한다. 각 묶음 수는 네 순서 위치에 한 번씩 나타나며 가능한 12개 방향의 인접 조합도 한 번씩 나타난다. 형상 순서도 회전한다.

| 프로세스 | 묶음 수 순서 |
|---|---|
| 0 | 16 → 32 → 128 → 64 |
| 1 | 32 → 64 → 16 → 128 |
| 2 | 64 → 128 → 32 → 16 |
| 3 | 128 → 16 → 64 → 32 |

같은 GPU·세션에서 순차적으로 실행하는 네 프로세스다. 통계적으로 독립인 날짜·GPU 표본을 네 개 확보한 것으로 해석하지 않는다.

## 판정

수집 완료, 안정성, 묶음 수 후보를 분리한다. 실행 내 IQR·절대 first/last drift가 각각 5% 이하이고 블록이 80 ms 이상이어야 한다. 같은 묶음의 네 프로세스 중앙값에 대해 `(최대−최소)/중앙값`이 5% 이하인지도 확인한다.

안정성 기준을 모두 통과한 조건에서, 후보 묶음과 그보다 큰 모든 묶음의 **모든 쌍**을 같은 프로세스끼리 비교한다. `큰 묶음 시간 / 작은 묶음 시간 − 1`이 네 프로세스 모두 ±1% 안이면 가장 작은 묶음을 후보로 표시한다. 중앙값만 같고 일부 실행에서 1%를 벗어나면 후보로 표시하지 않는다. 128회에는 더 큰 대조가 없으므로 그 자체를 충분하다고 판정하지 않는다.

**1%는 이번 진단에 미리 정한 실용 비교 기준**이며 기존 5% 안정성 gate를 대신하지 않는다. 네 번의 관측만으로 통계적 동등성, 잔여 제출 비용 0, 실제 오차 1% 이하를 보증하지 않는다. Graph 노드·캐시·GPU 상태의 영향은 남는다. 128회까지 계속 줄어들거나 변동이 크면 원자료를 검토해 다음 범위를 결정한다. 자동으로 크기를 늘리거나 full을 시작하지 않는다.

## 보존과 재분석

기존 v5의 13개 파일 hash·프로토콜·GPU 환경을 검사한다. 별도 GPU lock은 v5와 같은 `/tmp/gemm-sweep-<UUID>.lock`을 사용한다. 관측된 GNOME portal의 정확한 경로만 기록 후 허용하는 기존 정책을 재사용하고 다른 GPU 작업을 차단한다. 상태 변경·패키지 설치·clock 또는 power 조절은 없다. 1초 telemetry와 실행 전후 프로세스 목록을 보존한다. 이 목록은 데스크톱 GPU 간섭이 없다는 보증이 아니다.

`audit_support.py`는 검증된 `timing_audit_v4/audit.py`의 변경 없는 복사본이다. source 확인·import·프로세스 검사·로그/중단 처리·ZIP 생성 함수만 사용한다. 그 파일에 있는 NSYS 실행/worker 경로는 호출하지 않는다. 실행 환경 검사에서 nsys/ncu 버전만 읽고 profiler는 켜지 않는다.

출력은 raw 결과·환경·telemetry·실행 소스·기준 소스·manifest·상태·`analysis.json`·전체 정밀도 `summary.csv`·반올림한 `REPORT.md`를 포함한다. launcher 로그가 닫힌 뒤 ZIP과 SHA-256을 생성한다. CPU 테스트는 다음과 같다.

```bash
python3 -B -m unittest discover -s graph_batch_v1 -p 'test_*.py'
```

아직 GPU에서 이 새 패키지를 실행하지 않았다. 로컬 검사는 캡처 호출 수·측정 정규화·순서 균형·누락/손상 감지·수렴 판정·실패 로그 보존을 검증한다.
