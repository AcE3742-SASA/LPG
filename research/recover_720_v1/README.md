# 720 MHz 본측정 이어가기

정상 14구간의 1,680측정을 새 결과 폴더에 그대로 가져오고, 마지막 문제 구간 120개와 미수집 1,800개를 순서대로 측정한다. 추가 수집은 1,920개다. 기존 `abstract_sweep_725_v1` 측정기와 의존 폴더를 그대로 사용한다.

## 실행

ZIP을 풀어 `recover_720_v1` 폴더를 Ubuntu `/home/eu/gemm-research/scripts/`에 넣는다. 기존 폴더에 덮어쓰거나 재설치하지 않는다. 다음 두 원자료가 원래 위치에 있어야 한다.

- `abstract_sweep_725_v1/runs/abstract_200_720_20260921_20260921_213639_262a4a.zip`
- `abstract_sweep_725_v1/runs/check_720_repeat_20260921_190318/`

현재 tmux 안에서 한 번 실행한다. 새 세션·창을 만들거나 Enter 입력을 기다리지 않는다.

```bash
bash /home/eu/gemm-research/scripts/recover_720_v1/launch.sh
```

먼저 CPU에서 원본 ZIP·점검 자료·기존 코드와 의존 파일·정상 구간을 검사한다. `RECOVERY READY: imported=1680, pending=1920` 이후 기존 측정기를 실행한다. sudo 비밀번호는 클럭 설정·해제를 위해 기존 실행기에서 요청할 수 있다. 예상 약 2~3시간은 앞선 측정 속도에 근거한 계획값이다. 측정 중 파일 전송이나 다른 GPU 작업은 피한다.

진행 표시는 20초마다 기존 `progress.json`의 저장 건수를 읽는다. 첫 표시는 `1,680/3,600 (46.7%) | 남음 1,920 | 추가 수집 0/1,920`이며 처음에는 180초 예열 등으로 숫자가 유지될 수 있다. 표시용 GPU 조회·DB 접근은 없다. 100%는 기록 수집 완료이며 검산·클럭 해제·결과 ZIP 생성까지 기다린다. 표시가 품질 PASS를 뜻하지는 않는다.

결과는 `abstract_sweep_725_v1/runs/abstract_200_720_recovery_20260921/`에 쌓이며 종료 시 기존 실행기가 `RESULT_ZIP=` 경로를 출력한다. 그 ZIP을 전달한다. 정상적인 일시중단 뒤 같은 명령을 다시 실행하면 저장된 측정을 건너뛴다. 준비 도중 중단돼 완료 영수증이 없거나 새 클럭·데이터 문제가 생긴 경우는 보존 후 검토가 필요하며 자동으로 덮어쓰지 않는다.

## 보존과 판정

- 코어 720 MHz·메모리 6801 MHz·70 W, 예열·정확성·블록·회차·정확 클럭 일치 기준을 그대로 유지한다. 6800 MHz 표본을 통과시키는 예외는 추가하지 않는다.
- 기존 3,600개 계획·task ID·입력·순서·200형상·세 방식·Graph 묶음 선택을 유지한다. 앞선 회차 일부는 이전 worker, 나머지는 새 worker에서 수집된다. 최종 회차 간 변동은 기존 분석기로 다시 판정한다.
- 원래 문제 구간 120개는 새 분석 DB에서 제외하고 전부 다시 수집한다. 원본 1,800시도 전체와 실패 근거는 `recovery/source_run.zip`에 바이트 그대로 보존한다. 원본 결과 폴더는 수정하지 않는다.
- 가져온 원래 session의 `ERROR`·1,800건 기록 및 failed launch 상태도 그대로 둔다. `recovery_provenance.json`에 원래 1,800개 중 1,680개만 가져왔다는 이력을 명시한다. 원본 실패를 성공으로 바꾸지 않는다.
- 초기 결과는 1,680 PASS / 1,920 미수집인 `INCOMPLETE`다. 수집을 끝내도 누적 카운터 미해결로 전체 `REVIEW`/종료 코드 2가 남을 수 있으므로 완료 수·센서·회차·클럭 해제 근거를 함께 확인한다.

로컬 CPU 검증: `python3 -B recover_720_v1/test_recovery.py --archive 원본ZIP --check 점검폴더`. GPU를 실행하지 않는다.
